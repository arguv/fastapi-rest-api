# FastAPI Task Management REST API — Step-by-Step Project Explanation

> **Project:** `fastapi-rest-api`
> **Status:** Steps 1–9 completed; Step 10 (Dockerizing the FastAPI application) is next.
> **Stack:** Python 3.10, FastAPI, Pydantic, SQLAlchemy 2.x, PostgreSQL 17, psycopg 3, Alembic, pytest, Docker Compose.

## 1. What are we building?

A Task Management REST API. A client sends HTTP requests to create, list, retrieve, update, and delete tasks. The server validates input, executes business operations, and persists tasks in PostgreSQL.

A task currently contains:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | integer | Unique task identifier generated by PostgreSQL |
| `title` | string, max 255 in DB | Required task title |
| `description` | optional string | Additional task details |
| `completed` | boolean | Whether the task is finished; defaults to `false` |
| `priority` | `low`, `medium`, `high` | Priority; defaults to `medium` |

### HTTP endpoints

| Method | Path | Purpose | Typical success status |
| --- | --- | --- | --- |
| GET | `/health` | Check API health | 200 |
| POST | `/tasks` | Create a task | 201 |
| GET | `/tasks` | List tasks | 200 |
| GET | `/tasks/{task_id}` | Get one task | 200 |
| PUT | `/tasks/{task_id}` | Replace editable task fields | 200 |
| DELETE | `/tasks/{task_id}` | Delete a task | 204 |

Invalid Pydantic input returns **422**; a missing task returns **404**.

### Architecture

```text
HTTP client (curl / browser / frontend)
                 |
                 v
           FastAPI routes (main.py)
                 |
          Pydantic validation
                 |
        SQLAlchemy ORM + Session
           (models.py, database.py)
                 |
             psycopg driver
                 |
            PostgreSQL 17

Alembic (alembic/) ---> PostgreSQL schema migrations
pytest (tests/) ------> separate PostgreSQL test database
Docker Compose ------> PostgreSQL container (so far)
```

FastAPI is roughly analogous to a PHP web framework's controller/routing layer. Pydantic resembles validated request/response DTOs. SQLAlchemy ORM plays a role similar to Doctrine ORM, and Alembic resembles Doctrine Migrations.

## Step 6 — Update tasks using PUT

**Goal:** Modify an existing task.

```http

```

The current API uses `TaskCreate` for PUT, so it replaces all editable fields using the submitted values **and their defaults**. This is different from a partial update (`PATCH`). For example, omitting `completed` in PUT resets it to `false`.


## Step 9.3 — Connect Python to PostgreSQL

Install the driver and ORM:

```bash
python -m pip install sqlalchemy 'psycopg[binary]'
```

**File:** `database.py`

```python
from sqlalchemy import create_engine, text
from sqlalchemy.orm import sessionmaker

DATABASE_URL = (
    "postgresql+psycopg://"
    "task_user:<password>@localhost:5432/task_manager"
)

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    expire_on_commit=False,
)


def get_db():
    with SessionLocal() as db:
        yield db


def check_database_connection():
    with engine.connect() as connection:
        return connection.execute(
            text("SELECT current_database(), current_user")
        ).fetchone()
```

Test:

```bash
python -c 'from database import check_database_connection; print(check_database_connection())'
```

Expected:

```text
('task_manager', 'task_user')
```

**Explanation:** `engine` manages connectivity and connection pooling. `SessionLocal` creates SQLAlchemy sessions, which track ORM objects and database operations. `get_db()` is a FastAPI dependency that gives each request a session and closes it afterward. `yield` separates setup from cleanup.

**Important:** `localhost` works because FastAPI currently runs on the host machine. When FastAPI itself runs in Docker, the database hostname will normally be the Compose service name `db`, not `localhost`.

## Step 9.4 — Define the SQLAlchemy model and create the table

**File:** `models.py` (current model after Step 9.7):

```python
from sqlalchemy import Boolean, Integer, String, Text, text
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class Task(Base):
    __tablename__ = "tasks"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    title: Mapped[str] = mapped_column(String(255), nullable=False)
    description: Mapped[str | None] = mapped_column(Text, nullable=True)
    completed: Mapped[bool] = mapped_column(
        Boolean, default=False, nullable=False
    )
    priority: Mapped[str] = mapped_column(
        String(20),
        nullable=False,
        default="medium",
        server_default=text("'medium'"),
    )
```

The **original** model did not include `priority`; that column was added later via Alembic.

Initially, we created the development table using `scripts/create_tables.py`:

```python
from database import engine
from models import Base, Task

Base.metadata.create_all(bind=engine)
```

```bash
python -m scripts.create_tables
```

**Explanation:** `Base.metadata` contains table definitions collected from ORM models. `create_all()` creates missing tables but **does not replace schema migrations**: it cannot reliably express an ordered history of changes to existing tables.

Inspect the database:


## Step 9.5 — Move CRUD operations to SQLAlchemy

**Goal:** Store and retrieve real rows instead of Python in-memory objects.

Current `main.py` core (after adding priority):

```python
from typing import Annotated, Literal

from fastapi import Depends, FastAPI, HTTPException, status
from pydantic import BaseModel, ConfigDict
from sqlalchemy import select
from sqlalchemy.orm import Session

from database import get_db
from models import Task

app = FastAPI(title="Task Manager API")
DbSession = Annotated[Session, Depends(get_db)]


class TaskCreate(BaseModel):
    title: str
    description: str | None = None
    completed: bool = False
    priority: Literal["low", "medium", "high"] = "medium"


class TaskResponse(TaskCreate):
    model_config = ConfigDict(from_attributes=True)
    id: int


@app.get("/health")
def health_check():
    return {"status": "ok", "service": "task-manager-api"}


@app.post("/tasks", response_model=TaskResponse,
          status_code=status.HTTP_201_CREATED)
def create_task(task: TaskCreate, db: DbSession):
    new_task = Task(**task.model_dump())
    db.add(new_task)
    db.commit()
    db.refresh(new_task)
    return new_task


@app.get("/tasks", response_model=list[TaskResponse])
def list_tasks(db: DbSession):
    return db.scalars(select(Task).order_by(Task.id)).all()


@app.get("/tasks/{task_id}", response_model=TaskResponse)
def get_task(task_id: int, db: DbSession):
    task = db.get(Task, task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    return task


@app.put("/tasks/{task_id}", response_model=TaskResponse)
def update_task(task_id: int, task: TaskCreate, db: DbSession):
    existing_task = db.get(Task, task_id)
    if existing_task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    for field, value in task.model_dump().items():
        setattr(existing_task, field, value)
    db.commit()
    db.refresh(existing_task)
    return existing_task


@app.delete("/tasks/{task_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_task(task_id: int, db: DbSession):
    task = db.get(Task, task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    db.delete(task)
    db.commit()
```

### Important ORM operations

| Operation | Meaning |
| --- | --- |
| `Task(**task.model_dump())` | Convert validated request fields into a SQLAlchemy model |
| `db.add(obj)` | Mark a new object for insertion |
| `db.commit()` | Commit transaction changes |
| `db.refresh(obj)` | Reload generated/current values from DB |
| `db.get(Task, id)` | Retrieve a row by primary key |
| `select(Task).order_by(Task.id)` | Build a SELECT query |
| `db.scalars(...).all()` | Execute and return ORM objects |
| `db.delete(obj)` | Mark an object for deletion |

**Verification:** We created `PostgreSQL Task`, checked it using SQL, restarted Uvicorn, and confirmed the record still existed. This proved persistence across application restarts.

## Step 9.6 — Isolate automated tests in their own database

**Goal:** Prevent destructive test setup/teardown from touching development data.

Databases:

| Database | Purpose |
| --- | --- |
| `task_manager` | Development data |
| `task_manager_test` | pytest integration tests |
| `task_manager_migration_test` | Verify migrations on a clean schema |

Core test setup in `tests/test_tasks.py`:

```python
import pytest
from fastapi.testclient import TestClient
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

from database import get_db
from main import app
from models import Base

TEST_DATABASE_URL = (
    "postgresql+psycopg://task_user:<password>"
    "@localhost:5432/task_manager_test"
)
test_engine = create_engine(TEST_DATABASE_URL)
TestingSessionLocal = sessionmaker(
    bind=test_engine, autoflush=False, expire_on_commit=False
)


@pytest.fixture(autouse=True)
def setup_test_database():
    Base.metadata.create_all(bind=test_engine)
    yield
    Base.metadata.drop_all(bind=test_engine)


@pytest.fixture
def client():
    def override_get_db():
        with TestingSessionLocal() as db:
            yield db

    app.dependency_overrides[get_db] = override_get_db
    try:
        with TestClient(app) as test_client:
            yield test_client
    finally:
        app.dependency_overrides.clear()
```

**Explanation:** Dependency overrides redirect the application's database session to the test database. The autouse fixture creates and drops test tables around each test. **Never point `test_engine` at the development database**: `drop_all()` removes tables and data.

The fixture builds tables from SQLAlchemy metadata, not by executing Alembic. Therefore, ordinary API tests and migration-history tests verify different things.

### 9.7.2 Configure model metadata and database URL

In `alembic/env.py`, import your models and metadata:

```python
import os
from database import DATABASE_URL
from models import Base, Task

config.set_main_option(
    "sqlalchemy.url",
    os.getenv("ALEMBIC_DATABASE_URL", DATABASE_URL),
)

```

The rest of the Alembic-generated `env.py` remains intact.

**Explanation:** `target_metadata` tells Alembic what schema the SQLAlchemy models describe. The optional `ALEMBIC_DATABASE_URL` allows migration commands to target a separate database without editing the default development connection.

### 9.7.3 Establish the initial revision

```bash
alembic revision --autogenerate -m "initial tasks schema"
```

Revision ID: `0fdbf15e0645`.

**Important history:** We generated this revision against a database where `tasks` already existed. Therefore, Alembic initially generated empty `upgrade()`/`downgrade()` functions. We used `alembic stamp head` to mark that schema as already applied **without running SQL**.

```bash
alembic stamp head
alembic current
```

`stamp` only updates Alembic version tracking; `upgrade` actually executes migration operations. This distinction is essential.

### 9.7.4 Add task priority via a migration

First, add the `priority` field to the SQLAlchemy `Task` model. Then:

```bash
alembic revision --autogenerate -m "add task priority"
```

Revision ID: `cc7cf3a88d42`.

Generated migration:

```python
def upgrade() -> None:
    op.add_column(
        "tasks",
        sa.Column(
            "priority",
            sa.String(length=20),
            server_default=sa.text("'medium'"),
            nullable=False,
        ),
    )


def downgrade() -> None:
    op.drop_column("tasks", "priority")
```

Apply to development:

```bash
alembic upgrade head
alembic current
```

**Why `server_default`?** The existing table had rows. PostgreSQL can populate the new non-nullable column with `medium` for those rows and use that default for future inserts that omit priority. `default="medium"` is an ORM-side default; `server_default` is a database-side default.

**Caution:** `downgrade()` drops the column, so priority values are lost if that downgrade is executed.

### 9.7.5 Expose priority in FastAPI

Update the Pydantic model:

```python
from typing import Literal

class TaskCreate(BaseModel):
    title: str
    description: str | None = None
    completed: bool = False
    priority: Literal["low", "medium", "high"] = "medium"
```

`TaskResponse` inherits this model and adds `id`. Requests with `priority="urgent"` return 422. Omitting priority produces `medium`.

**Important nuance:** Pydantic validates the API input, but the database column is still just `VARCHAR(20)`. Direct SQL writes could insert other strings unless a database CHECK constraint or enum is added later.

### 9.7.7 Fix the initial migration for fresh databases

We discovered that an empty initial revision would not create the `tasks` table in a new environment. We corrected the existing initial migration file `alembic/versions/0fdbf15e0645_initial_tasks_schema.py`:

```python
def upgrade() -> None:
    op.create_table(
        "tasks",
        sa.Column("id", sa.Integer(), primary_key=True),
        sa.Column("title", sa.String(length=255), nullable=False),
        sa.Column("description", sa.Text(), nullable=True),
        sa.Column("completed", sa.Boolean(), nullable=False),
    )


def downgrade() -> None:
    op.drop_table("tasks")
```

Verify syntax:

```bash
python -m compileall -q alembic/versions
```

**Why this was safe in our local workflow:** The initial revision had already been stamped as applied in the existing development database, so changing its contents did not rerun it there. **General best practice:** Avoid modifying migration files after they have been shared/applied across multiple environments. We made this correction during local learning before a real deployment.

## Full request lifecycle: What happens when we create a task?

Request:

```bash
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Learn Alembic","description":"Practice migrations","priority":"high"}'
```

1. **Uvicorn** receives the HTTP request and passes it to the FastAPI ASGI application.
2. **FastAPI routing** selects `POST /tasks`.
3. **Pydantic** parses the JSON into `TaskCreate`, validates `priority`, and applies `completed=False` if omitted.
4. **Dependency injection** calls `get_db()` and supplies a SQLAlchemy session.
5. **Controller function** creates a `Task` ORM instance using `task.model_dump()`.
6. **SQLAlchemy** schedules and commits the INSERT using the session.
7. **psycopg** communicates with PostgreSQL.
8. **PostgreSQL** stores the row and generates its ID.
9. **SQLAlchemy** refreshes the object from the database.
10. **Pydantic response model** serializes the ORM object to JSON.
11. **FastAPI** returns HTTP **201 Created**.
12. **Dependency cleanup** closes the SQLAlchemy session.

Observed response:

```json
{
  "title": "Learn Alembic",
  "description": "Practice migrations",
  "completed": false,
  "priority": "high",
  "id": 2
}
```

### Where validation and defaults live

| Layer | Example | Responsibility |
| --- | --- | --- |
| Pydantic | `Literal["low", "medium", "high"]` | Reject invalid API input |
| Pydantic | `priority = "medium"` | Default missing API field |
| SQLAlchemy | `default="medium"` | ORM-side default for inserts |
| PostgreSQL | `DEFAULT 'medium'` | Database-side default when SQL omits field |
| PostgreSQL | `NOT NULL` | Disallow null values |
